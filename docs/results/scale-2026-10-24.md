# Filter step time at scale, 2026-10-24

`scripts/verify/scale_bench.py` (perf/scale): `apply_filter` on fixed seeded states, N = 16, 32, 64 and 128, two densities, 5 warm-up and 50 timed steps per config, each config in its own process, zero nominal acceleration and the fuzz.py closed loop (one latch dict per run).

- **dense**: groups of 8 drones, each a fuzz.py-style converging encounter (miss up to about 6 m, closest approach 2-4 s after the start, so inside the timed window), group centres on a jittered 80 m grid at 80-150 m, so neighbouring groups also meet. The N = 64 sweep varies the group size from 2 to 64 (64 = one converging cluster of all drones).
- **city**: drones over x, y in [100, 900] m and z in [60, 160] m, at least 30 m apart, 5-15 m/s on random, mostly horizontal headings.

Machine: Intel(R) Xeon(R) Processor @ 2.80GHz (KVM guest, Cascade Lake class, AVX-512), 4 logical cores, 1 thread per core, Linux 6.18, Python 3.12.3, numpy 1.26.4, scipy 1.17.1, osqp 0.6.7.post3, numba 0.68.0. BLAS/OpenMP threads pinned to 1 (`OMP_NUM_THREADS=1`); the Numba rollout of perf/scale uses all 4 cores from 256 pairs. One run per config, run one at a time on an otherwise idle machine. This machine is not the founder's laptop (6 cores / 12 threads, Windows 11): absolute times differ, ratios and the split carry over.

The split is the mean exclusive time per timed step (a nested timed call is not counted twice), measured by wrapping filter-module functions from outside, so the older commits run unchanged: QP build = `build_hocbf_qp_matrices` of the first solve; OSQP setup; OSQP solve including the alpha-1.0 retry; escape stage = the escape re-solve (its build, setup and solve) and `_escape_signs`; `_update_latches`; backup rollout = `_backup_constraints` (rollout and row derivation); everything else = pair loop, diagnostics, contract objects, fallback. "max cluster" is the largest connected set of latched pairs (0 at 883b9c2, which has no latch). "actions hash" hashes every filtered action of the run: equal hashes mean bit-identical behaviour.

The founder's 2136 ms on main is the last row (out of scope for the step-time target, founder decision 2026-10-24: preventing a 64-drone converging cluster is the strategic layer's job): one converging cluster of 64 drones (2021 ms here). The earlier 165-390 ms were spread states, which here are the rows with groups of 2-8 and the city rows (288-449 ms).

What grows, in order of size:

1. **OSQP solve, 129 → 549 ms at a fixed problem size.** The joint QP always has 2016 pair rows, 192 accelerations and 2016 slacks, so setup (5 → 8 ms) and the build (17-19 ms) barely move. What moves is the number of ADMM iterations: in a large cluster many rows are active at once, and from 32 drones up OSQP hits `max_iter` = 4000, retries at alpha 1.0, hits it again and the step falls back (21 and 24 of 50 timed steps are solver errors; 1.7-1.8 solves per step). Those steps set the p95.
2. **`_update_latches`, 46 → 224 ms.** The per-pair screen costs the same at every group size (2016 pairs); the growth is the entering path. On steps where pairs enter conflict it colours the whole conflict set: the colouring graph is every pair inside each cluster of three or more drones (c²/2 per cluster), and `_escape_signs` / `_new_latch` call `_escape_axes` → `_lateral` (small numpy operations, about 15-20 µs each) for every pair in it. At c = 32 the profile shows 33 724 `_escape_axes` and 50 275 `_lateral` calls in 55 steps.
3. **Escape stage and fallback, 0 → 89 + 58 ms**, only from 32 drones up, where pairs keep slack (escape re-solve with rho 10) and the solver errors trigger `_fallback_cluster` (per-agent `_pair_constraint` loops, 120 544 calls).

The backup rollout (74-82 ms) and the build do not depend on the group size.

How each component scales with N (dense, groups of 8; pairs M = N(N-1)/2 grow 4x per doubling of N):

| N | pairs | OSQP solve | `_update_latches` | rollout | build |
| --- | --- | --- | --- | --- | --- |
| 16 | 120 | 4.1 | 5.1 | 4.3 | 3.9 |
| 32 | 496 | 22.6 | 18.1 | 19.7 | 6.7 |
| 64 | 2016 | 166.6 | 61.8 | 77.8 | 18.8 |
| 128 | 8128 | 1698.8 | 221.6 | 293.1 | 69.2 |

Rollout and `_update_latches` are linear in the pair count (4x and 3.5x per doubling of N, that is about N²). The OSQP solve grows 5.5x, 7.4x and 10.2x per doubling, about M^1.2 to M^1.7 (N^2.5 to N^3.3), because every pair of the fleet is a row of one QP (no range gate, `range_gate_m=None`) and the iteration count also grows with the number of rows.

Across the commits (N = 64, one cluster of 64): 883b9c2 p95 1307 ms (no latches; numpy rollout 168 ms); 502e3fc (#12) 2043 ms: `_update_latches` adds 219 ms and the fallback and escape work grows with the latch behaviour; dae9066 2021 ms: the Numba rollout (#22) saves 116 ms of mean time (193 → 78 ms), but the p95 is set by the solve, so it hardly moves. At groups of 8, #12 added 61 ms of `_update_latches` and 40 ms of rollout (latched axes; 154 → 193 ms), p50 327 → 430 ms, and #22 removed 116 ms of rollout time (p50 309 ms).

## Exactness

Rule: `compare_results.py --tolerance 1e-4` on the full tier against `docs/results/pr12-b1-2026-10-23.jsonl`. On this machine main itself is not bit-exact against that Windows file: quick tier at dae9066, max |Δ min_sep| = 3.49e-10 m on 88 rows, all integer fields and the d_eff set identical (tolerance mode PASS). So each change was also compared bit for bit against main run here (`vq_main`).

- **A + B + D (kept), quick tier:** exact against main on this machine: 413/413 rows, every field equal, max |Δ min_sep| = 0. Against the reference with tolerance 1e-4: PASS, max |Δ min_sep| = 3.49e-10 m (the platform difference above). Every scale_bench config: actions hash identical to main (13/13 configs).
- **A + B + D, full tier** (`tier.py full` at 89c2898; later commits change only docs, tests and the benchmark): fuzz 10000/10000 rows bit for bit against main's full tier on this machine (every field, max |Δ min_sep| = 0). Against the reference with tolerance 1e-4: PASS, 10000/10000, max |Δ min_sep| = 2.4e-9 m; 0 normal-fuzz runs and 13 hard runs inside d_eff, 0 fallbacks, 0 solver errors, 0 exceptions, as in the reference. The tier's own exact compare against the Windows file fails here for main too (1684 rows differ in the last digits of min_sep). Every other script: ok; `det.py` identical across two processes; every script log (all 15 of the tier, including both `det.py` runs) identical to main's full tier on this machine, apart from the checkout path in the compare log.
- **C (rejected), quick tier:** against the reference with tolerance 1e-4: **FAIL**, 118 of 413 rows off by more than 1e-4 m, max 0.163 m (fuzz seed 122: 6.237 → 6.075 m); 52 rows worse and 66 better by more than 1e-4 m. Integer fields (fallback, solver errors, first step inside, rollout steps, cap hits, aborts) identical on every row, and the same 13 seeds inside d_eff. Rejected under the rule, not tuned; reverted in fae327c.
