## 2026-10-24 (verification speed, PR 2: backup rollout kernel)

Decided by Claude under the Decision authority rules (performance work that reproduces the per-seed results file exactly). The founder chose Numba for this PR.

- **`_backup_rollout` runs in a Numba kernel.** `_rollout_kernel` (`@njit(cache=True)`, no fastmath) flies one pair at a time with scalar loops. It inlines `_lateral` (default `plumb_sin`), `_frame_lateral`, `_world_accel_limits` and `_evasive_direction`, which stay as numpy for every other caller. `_backup_rollout` keeps its signature and return values. `numba>=0.60,<1` is a new runtime dependency.
- **Bit-exact by construction on finite float64 inputs, checked three ways.** The kernel repeats numpy's floating-point operations in numpy's order. Measured on this machine (numpy 1.26.4): `np.linalg.norm` and `np.sum` over a row add x, y, z left to right; `np.einsum("ij,ij->i")` adds x and z, then y. Checks: (1) `tests/test_filter_rollout_kernel.py` compares the kernel with the old numpy rollout bit for bit on random pairs (walls, vertical and near-vertical lines of sight, latched axes and z directions, rollouts past the minimum and at the cap). (2) `compare_results.py` exact on the full tier with early stop and with `--no-early-stop` (10000/10000 rows each, max |Δ min_sep| 0, all fields equal), as the early-stop entry asks for a filter change. (3) Every verify script of the full tier prints the same output as on PR 1 (the logs differ only in the worktree path and the progress prefix).
- **known limit: the einsum order is numpy's, not a standard.** Another numpy build or CPU (CI runs Python 3.11 with a newer numpy) may add the closing rate in another order. The oracle test compares the returned closing speed bit for bit, so it would fail there (likely on aarch64, where numpy's einsum uses fused multiply-add; x86 with numpy 2.3.5 matches). The filter uses the closing speed only for the stop decision, so only a pair whose closing speed is within about 1 ulp of 0 could change, and the reference results would still match in practice. Revisit if the oracle test fails on another platform.
- **Inputs are validated before the kernel.** Numba does not check bounds, and the kernel's `max`/`min` do not propagate NaN as `np.maximum`/`np.clip` do. `_backup_rollout` therefore raises `ValueError` on mismatched shapes (where numpy raised or broadcast) and on non-finite inputs (where numpy returned NaN). Callers pass full-shape, finite float64 arrays (the contracts forbid inf/NaN), so results are unchanged. Inputs are converted to float64 (a float32 input used to compute in float32; no caller passes one).
- **Timings (idle machine, 6 cores / 12 threads; PR 1 after-timings → this PR).** Default `pytest` 87.4 s → 20.8 s (min of 3), quick tier 240.4 s → 27.0 s (min of 3), slow suite 604.1 s → 90.2 s (1 run), full tier about 134 min → 1182 s = 19.7 min (1 run; fuzz 534 s, `recov` 638 s and `optbound` 636 s are the longest steps). The founder cut the slow and full timings to one run each and dropped the on-demand `invariance.py` rerun; that one full run also rechecked exactness after the input validation (10000/10000, max |Δ min_sep| 0, every script output the same as on PR 1).
- **Not done in this PR: the N = 64 step-time stretch target.** At 64 drones (`apply_filter` alone, 100 steps of a converging cluster) the p95 is 2313 ms before and 2136 ms after. There the rollout is 4 % of filter time; `osqp.solve` (45 %, 322 ms per solve over 2016 pairs) and `_update_latches` (40 %) dominate. OSQP warm start, per-cluster QPs and broad-phase pair skipping change the solution numerically, so each needs its own tolerance check on the full tier. Left for a later PR.

- **`scripts/verify/scale_bench.py` is the standard step-time benchmark.** Fixed seeded states, N = 16, 32, 64, 128, dense (converging groups, `--cluster` sets the group size) and city spread, 5 warm-up and 50 timed steps, one process per config. It reports p50/p95 and an exclusive time split, and hashes every filtered action so two versions can be compared on the same states. It measures other checkouts unchanged (`--src`) by wrapping filter-module functions from outside instead of adding timers to the filter.
- **The 2136 ms gap is cluster size.** At N = 64 on main, with the same 2016 pairs in the joint QP, p95 goes from 322 ms (groups of 2) to 2021 ms (one cluster of 64). The OSQP solve grows from 129 to 549 ms mean (more active rows, `max_iter` hit twice per step from 32 drones up, 24 of 50 steps solver errors at 64). `_update_latches` grows from 46 to 224 ms (the entering path colours every pair inside a cluster of three or more). Escape and fallback grow from 0 to 147 ms (every fallback step is a solver error). The founder's 2136 ms is consistent with the one-cluster row (other machine, 100 steps against 50 timed). Across commits at a 64-cluster, p95 went 1307 → 2043 ms (+736) from 883b9c2 to 502e3fc: 219 ms is the mean `_update_latches` component, the rest is solve, escape and rollout growth under the latched behaviour. The earlier 165-390 ms were spread states.
- **Exactness on this machine.** The reference file was made on Windows. Here (Linux, Python 3.12, numpy 1.26.4, osqp 0.6.7) main itself matches it only within 3.49e-10 m (88 of 413 quick-tier rows differ in the last digits; integer fields and the d_eff set are identical). Kept changes are therefore held to two checks: tolerance 1e-4 against the reference (the rule) and bit for bit against main run on the same machine.
- **Kept, bit-exact:** (A) `_conflict_screen` vectorises the `_update_latches` enter/release tests; pairs within 1e-9 relative of a threshold are decided by the per-pair code, so every decision is the loop's. (B) `build_hocbf_qp_matrices` builds the pair rows directly in sparse form (exact zeros dropped as the dense-to-CSC conversion did), and `_backup_constraints` gathers pair states from one array per agent. (D) the backup rollout runs over threads (`prange`) from 256 pairs; pairs are independent, so it returns the serial kernel's arrays bit for bit, and every fuzz run (at most 15 pairs) stays serial. Oracle tests: `tests/test_filter_scale.py` (screen against the loop, sparse build against the dense-row build, both barriers, escape rows, exact-zero rows) and `test_parallel_kernel_matches_serial_kernel`.
- **Caveats of D (from the PR #24 review).** Numba picks the `omp` threading layer on Linux, which is not fork-safe: a process that has run the parallel kernel (24 drones or more) and then forks (the default `multiprocessing` start method on Linux up to Python 3.13) gets children that abort. The first step above 256 pairs compiles the parallel kernel when the on-disk Numba cache is cold (seconds, once). A hovering fleet (all v = 0) has r . v = 0 on every pair, so A's screen sends every pair to the scalar fallback and costs the old loop plus the vector pass (still exact).

Rejected under the exactness rule, not tuned; reverted in fae327c. Cause: OSQP's polished answer is off by up to about 1e-2 m/s² near box bounds, and how far depends on which drones share the QP.

## 2026-10-24 (scale lane, perf/solver-exact: KKT-exact QP, option 1 step 2)

Founder decision 2026-10-24 (option 1 of `docs/architecture/PROPOSAL-scale-qp.md`); the choices below were made by Claude under it. Numbers: `docs/results/solver-exact-2026-10-24.md`.

- **Solver: DAQP up to 256 variables, OSQP at eps 1e-9 above, each the other's fallback, every solution KKT-certified.** Measured on 21 259 fuzz QPs and joint QPs at N = 16-64 (`scripts/verify/solver_compare.py`). DAQP, tight OSQP and proxsuite agree within 5e-8 m/s² on all 21 259 fuzz QPs and pass the certificate on all of them; DAQP is as fast as the old OSQP there (0.56 against 0.62 ms). ## 2026-10-24 (scale lane, perf/solver-exact: bounded step time, contract v1.5)

Founder decision 2026-10-24 (before merging PR #26): per-cluster solve deadlines from the 100 ms step, most urgent first, backup on a missed deadline, one cluster never delays another. The choices below were made by Claude under it. Numbers: `docs/results/deadline-2026-10-24.md`.

- **Derivation of the deadline.**
  - The work after the solves gets a 10 ms reserve (measured at most 3.4 ms at N = 64, 9.6 ms at N = 128).
  - The solves of both stages get what is left of the 100 ms, at least 25 ms (above the 99.9th percentile of a whole solve stage at N = 64, 16.5 ms).
  - Within that window each cluster, in urgency order (smallest backup margin d* - d_eff first), has a guaranteed share proportional to its QP size. It may use what earlier clusters leave, never a later cluster's share (`_cluster_deadlines`).
  - DAQP and OSQP get the time left as their own time limit.
- **Backup on a miss:** each drone of the cluster flies `_evasive_accel` against its most critical neighbour in the cluster, the manoeuvre the backup rows simulate. Those drones get `qp_feasible=false`, `fallback_used=true` and the new `deadline_fallback=true`. A miss is not a solver error. A miss in the escape stage keeps the cluster's first solve.
- **Contract v1.5 (founder-directed):** `SafeAction.deadline_fallback` (default false; requires `fallback_used`), `FilterDiagnostics.deadline_fallback_agents`, and episode summary `deadline_fallbacks`, also counted in `fallback_events`. The planned `ScenarioConfig.disturbances` item moves to v1.6 and stays planned.
- **Escape stage reuses unchanged first-stage solutions:** bit-identical, since the same QP goes to the same deterministic solvers. It saves the escape stage's time.
- **`_backup_constraints` returns the backup margin as a fifth value**, for the urgency order. `test_filter_backup_horizon.py` unpacks five values, and the solver-wrapping tests in `test_filter_safety_core.py` pass `**kwargs` through. Their expectations are unchanged.
- **Results:**
  - Full tier bit-identical to the step-3 tier: no deadline hit in fuzz or in any verify script.
  - N = 64 (groups of 2-16, city) has no deadline hit; p95 62 ms dense (groups of 8) and city.
  - The single 64-drone cluster's worst step is 134 ms instead of 55 s.
- **Safety cost, accepted by the founder 2026-10-24 ("yes for now"):**
  - Groups of 32: min sep 5.591 m → 3.232 m, 21 steps inside d_eff (12 deadline steps).
  - One cluster of 64: 3.738 m → 1.264 m, 29 steps inside d_eff (19 deadline steps).
  - Both are against step 3 without a deadline, and both are still better than main (1.753 m and 0.909 m). The cause is that the pairwise backup (BL-02, BL-03) is weak in large clusters.
