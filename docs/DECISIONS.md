## 2026-10-23 (verification speed, PR 1: tooling)

Decided by Claude under the Decision authority rules (tooling that reproduces the per-seed results file exactly). Profile before the change: `docs/results/profile-2026-10-23.md`.

- **`compare_results.py` is the exactness gate.** `scripts/verify/compare_results.py CANDIDATE.jsonl` matches rows on (mode, seed) against `docs/results/pr12-b1-2026-10-23.jsonl`. Default: every field identical, bit for bit (tooling changes). `--tolerance 1e-4`: integer fields and `exc` identical, the same seeds inside d_eff, and |Δ min_sep| ≤ 1e-4 m on every seed (numerical changes). A candidate may cover a subset of the reference (the quick tier). Tests in `tests/test_compare_results.py`.
- **`fuzz.py` collects results in the parent process (BL-09).** Workers return one dict per run; the parent prints one line per run in seed order with a progress and ETA prefix, and appends one JSONL row per run (the reference schema, sorted keys) to `--out`, flushed, so a killed run resumes from the rows it has. The old per-run `max_depth` and `hash` fields are dropped: `hash()` of bytes is salted per process, so `hash` never compared across runs. The positional arguments and `HARD=1` work as before; `run((seed, barrier, steps))` keeps its old behaviour, so the OSQP regression test, `det.py` and `recov.py` are unchanged.
- **Tiers.** `--tier quick`: seeds 0-199 normal and hard, plus the hard seeds the reference has inside d_eff (the 13 seeds ≥ 200), 413 runs. `--tier full`: seeds 0-4999 normal and hard. `scripts/verify/tier.py quick|full` runs the tier, compares it exactly, and for `full` runs every script of the README table except `invariance.py`, up to one per core at a time (`det.py` twice, outputs compared).
- **`invariance.py` moved to an on-demand tier (founder decision, 2026-10-24).** In the full tier it ran serially for 165 min (9909 s), alone after everything else had finished, so the full tier took 256 min instead of 134. It measures with the pre-latch escape model (P2-SA-02 §5.4), and `inv2.py` already covers the check in parallel within the full tier. It now runs only with `tier.py ondemand`.
- **Early stop (on by default in the CLI, `--no-early-stop` to fly all steps).** A run ends when the last filter step left the nominal untouched (no intervention, slack, fallback, solver error, world-limit conflict, capped or extended rollout), no pair is latched, every pair separates beyond its braking distance under 2 u_max (r·w > 0 and |r| − d_eff > |w|²/(4 u_max)), and the world-box limits allow zero acceleration at both ends of every drone's straight-line path over the remaining steps. Checked bit for bit against the reference on the quick tier (413/413) and the full tier (10000/10000 rows, max |Δ min_sep| 0, all fields equal). The conditions are sufficient in practice, not proven: a later filter change must rerun the full tier with and without `--no-early-stop` before the reference moves.
- **`slow` marker.** The 17 test functions that took 95 % of the full-suite time (fuzz seeds, sweeps, long closed-loop episodes; 16 listed in the profile, plus `test_vertical_head_on_under_noise_no_worse_than_horizontal`, which reads the same `functools.cache` rows as `..._keeps_one_sideways_direction` and so looked free in the serial profile) are marked `slow` (91 items; 172 fast). `pytest` runs the rest with `-n auto -m 'not slow'` (pytest-xdist, added to the dev extras); `pytest -m slow` runs the slow suite, `pytest -m ""` everything. CI runs the fast suite on every push and the slow suite on pull requests to main. No test expectation changed. The tests write only to `tmp_path`. The only module state shared between tests is that cache of pure, seeded results, so a worker that misses it recomputes the same rows: the parallel run is order-independent and only slower.

## 2026-10-24 (verification speed, PR 2: backup rollout kernel)

Decided by Claude under the Decision authority rules (performance work that reproduces the per-seed results file exactly). The founder chose Numba for this PR.

- **`_backup_rollout` runs in a Numba kernel.** `_rollout_kernel` (`@njit(cache=True)`, no fastmath) flies one pair at a time with scalar loops. It inlines `_lateral` (default `plumb_sin`), `_frame_lateral`, `_world_accel_limits` and `_evasive_direction`, which stay as numpy for every other caller. `_backup_rollout` keeps its signature and return values. `numba>=0.60,<1` is a new runtime dependency.
- **Bit-exact by construction on finite float64 inputs, checked three ways.** The kernel repeats numpy's floating-point operations in numpy's order. Measured on this machine (numpy 1.26.4): `np.linalg.norm` and `np.sum` over a row add x, y, z left to right; `np.einsum("ij,ij->i")` adds x and z, then y. Checks: (1) `tests/test_filter_rollout_kernel.py` compares the kernel with the old numpy rollout bit for bit on random pairs (walls, vertical and near-vertical lines of sight, latched axes and z directions, rollouts past the minimum and at the cap). (2) `compare_results.py` exact on the full tier with early stop and with `--no-early-stop` (10000/10000 rows each, max |Δ min_sep| 0, all fields equal), as the early-stop entry asks for a filter change. (3) Every verify script of the full tier prints the same output as on PR 1 (the logs differ only in the worktree path and the progress prefix).
- **known limit: the einsum order is numpy's, not a standard.** Another numpy build or CPU (CI runs Python 3.11 with a newer numpy) may add the closing rate in another order. The oracle test compares the returned closing speed bit for bit, so it would fail there (likely on aarch64, where numpy's einsum uses fused multiply-add; x86 with numpy 2.3.5 matches). The filter uses the closing speed only for the stop decision, so only a pair whose closing speed is within about 1 ulp of 0 could change, and the reference results would still match in practice. Revisit if the oracle test fails on another platform.
- **Inputs are validated before the kernel.** Numba does not check bounds, and the kernel's `max`/`min` do not propagate NaN as `np.maximum`/`np.clip` do. `_backup_rollout` therefore raises `ValueError` on mismatched shapes (where numpy raised or broadcast) and on non-finite inputs (where numpy returned NaN). Callers pass full-shape, finite float64 arrays (the contracts forbid inf/NaN), so results are unchanged. Inputs are converted to float64 (a float32 input used to compute in float32; no caller passes one).
- **Timings (idle machine, 6 cores / 12 threads; PR 1 after-timings → this PR).** Default `pytest` 87.4 s → 20.8 s (min of 3), quick tier 240.4 s → 27.0 s (min of 3), slow suite 604.1 s → 90.2 s (1 run), full tier about 134 min → 1182 s = 19.7 min (1 run; fuzz 534 s, `recov` 638 s and `optbound` 636 s are the longest steps). The founder cut the slow and full timings to one run each and dropped the on-demand `invariance.py` rerun; that one full run also rechecked exactness after the input validation (10000/10000, max |Δ min_sep| 0, every script output the same as on PR 1).
- **Not done in this PR: the N = 64 step-time stretch target.** At 64 drones (`apply_filter` alone, 100 steps of a converging cluster) the p95 is 2313 ms before and 2136 ms after. There the rollout is 4 % of filter time; `osqp.solve` (45 %, 322 ms per solve over 2016 pairs) and `_update_latches` (40 %) dominate. OSQP warm start, per-cluster QPs and broad-phase pair skipping change the solution numerically, so each needs its own tolerance check on the full tier. Left for a later PR.
