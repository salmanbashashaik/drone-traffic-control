## 2026-10-24 (verification speed, PR 2: backup rollout kernel)

Decided by Claude under the Decision authority rules (performance work that reproduces the per-seed results file exactly). The founder chose Numba for this PR.

- **`_backup_rollout` runs in a Numba kernel.** `_rollout_kernel` (`@njit(cache=True)`, no fastmath) flies one pair at a time with scalar loops. It inlines `_lateral` (default `plumb_sin`), `_frame_lateral`, `_world_accel_limits` and `_evasive_direction`, which stay as numpy for every other caller. `_backup_rollout` keeps its signature and return values. `numba>=0.60,<1` is a new runtime dependency.
- **Bit-exact by construction on finite float64 inputs, checked three ways.** The kernel repeats numpy's floating-point operations in numpy's order. Measured on this machine (numpy 1.26.4): `np.linalg.norm` and `np.sum` over a row add x, y, z left to right; `np.einsum("ij,ij->i")` adds x and z, then y. Checks: (1) `tests/test_filter_rollout_kernel.py` compares the kernel with the old numpy rollout bit for bit on random pairs (walls, vertical and near-vertical lines of sight, latched axes and z directions, rollouts past the minimum and at the cap). (2) `compare_results.py` exact on the full tier with early stop and with `--no-early-stop` (10000/10000 rows each, max |Δ min_sep| 0, all fields equal), as the early-stop entry asks for a filter change. (3) Every verify script of the full tier prints the same output as on PR 1 (the logs differ only in the worktree path and the progress prefix).
- **known limit: the einsum order is numpy's, not a standard.** Another numpy build or CPU (CI runs Python 3.11 with a newer numpy) may add the closing rate in another order. The oracle test compares the returned closing speed bit for bit, so it would fail there (likely on aarch64, where numpy's einsum uses fused multiply-add; x86 with numpy 2.3.5 matches). The filter uses the closing speed only for the stop decision, so only a pair whose closing speed is within about 1 ulp of 0 could change, and the reference results would still match in practice. Revisit if the oracle test fails on another platform.
- **Inputs are validated before the kernel.** Numba does not check bounds, and the kernel's `max`/`min` do not propagate NaN as `np.maximum`/`np.clip` do. `_backup_rollout` therefore raises `ValueError` on mismatched shapes (where numpy raised or broadcast) and on non-finite inputs (where numpy returned NaN). Callers pass full-shape, finite float64 arrays (the contracts forbid inf/NaN), so results are unchanged. Inputs are converted to float64 (a float32 input used to compute in float32; no caller passes one).
- **Timings (idle machine, 6 cores / 12 threads; PR 1 after-timings → this PR).** Default `pytest` 87.4 s → 20.8 s (min of 3), quick tier 240.4 s → 27.0 s (min of 3), slow suite 604.1 s → 90.2 s (1 run), full tier about 134 min → 1182 s = 19.7 min (1 run; fuzz 534 s, `recov` 638 s and `optbound` 636 s are the longest steps). The founder cut the slow and full timings to one run each and dropped the on-demand `invariance.py` rerun; that one full run also rechecked exactness after the input validation (10000/10000, max |Δ min_sep| 0, every script output the same as on PR 1).
- **Not done in this PR: the N = 64 step-time stretch target.** At 64 drones (`apply_filter` alone, 100 steps of a converging cluster) the p95 is 2313 ms before and 2136 ms after. There the rollout is 4 % of filter time; `osqp.solve` (45 %, 322 ms per solve over 2016 pairs) and `_update_latches` (40 %) dominate. OSQP warm start, per-cluster QPs and broad-phase pair skipping change the solution numerically, so each needs its own tolerance check on the full tier. Left for a later PR.

## 2026-10-24 (research lane: adaptive margin, P3-SA-03)

Research only: nothing here changes `src/` or `tests/`. Decided by Claude under the Decision authority rules unless marked otherwise. Code in `research/adaptive_margin/`; derivation and sources in P3-SA-03.

- **Risk level per check (for the founder).** P_RISK = 10⁻³, tied to the 99.9 % command-and-control reliability of 3GPP TS 22.125 Table 7.2-1. It sets K = 4.033 (3-D chi-square), the NIS bound and the single-loss rule. It is the main free choice in the margin; P3-SA-03 §8 asks the founder to confirm it and lists the other modelling choices.
- **Prototype wraps main, does not change it.** `sim.py` calls main's `apply_filter` with `FilterConfig(margin_m=...)` on predicted states, as any caller would. The filter takes one margin, so it gets the largest pair margin.
- **Actuator lag τ_a = 0.25 s.** The upper end of the former PX4 `MC_ROLL_TC` range (0.15–0.25 s). No measured lag exists for the target drones (P3-SA-03 §2.4).
- **Equivalent delay holds a0.** After the playout tick the prediction holds the actuator output a0 plus the disturbance estimate for τ_a, in closed form. The lag-minus-delay error is bounded by ½ τ_a² |Δc| and covered by `EPS_LAG_M` (0.758 m per pair); `check.check_lag_bound` verifies the bound.
- **Playout at the 99.9 % latency quantile.** Commands play out at P = 130 ms after the cycle, the 99.9 % quantile of the log-normal fitted to Barrios-Muñoz et al. 2024 at 60 m, rounded up to the tick. A later command is dropped and counted as lost.
- **Single-loss bound.** The margin covers one lost command per drone (`lost_bound`); a command sent in the current cycle is covered by `DU_NOW_M` = 0.120 m until it enters the log. Two losses in a row (10⁻⁶ at the 3GPP rate) raise `link` instead of widening the margin.
- **Position floor.** The margin uses a position covariance floored at the receiver's σ, because the sources give no GNSS error correlation time and a constant bias does not average out. The Kalman update uses the unfloored covariance.
- **NIS window of 10 messages (1 s).** Long enough for a chi-square test with 60 degrees of freedom, short enough to react within the 1 s offboard-loss timeout.
- **Tracker noise from the data.** q = 2 (D σ_g)² / τ_g per axis (the Gauss–Markov gust's stationary variance) and P_dd(0) = (D U)² + (D σ_g)², with floors 10⁻⁶ and 10⁻⁴ so calm conditions stay positive definite.
- **Disturbance model.** Wind only: d = D (W + gust), with D = 0.544 s⁻¹ (Faessler et al. 2018, largest coefficient) on all three axes. The drag of the drone's own motion is assumed handled by the autopilot. Gusts are independent between drones, which overstates relative gusts for close pairs (correlation length about 270 m).
- **Entry period of 2 s.** The monitor is read from 2 s on. At t = 0 the wind prior is the full forecast speed in an unknown direction, so every alarm fired at once; 2 s is 20 telemetry messages, two NIS windows. A real drone would join the managed airspace only after its tracker converged.
- **Wall alarm instead of a reduced A_REL.** Near a world-box wall the backup's braking is weaker than √2 u_max. The prototype raises `wall` there instead of computing the reduced value.
- **Full-echo shortcut.** The drone's telemetry echoes its whole command-switch history, so the ground station knows exactly which commands were applied. A real protocol would acknowledge commands.
- **Zero nominal action.** As in the PR #12 and P3-SA-02 runners, every drone proposes zero acceleration, so the filter alone resolves each encounter.
- **SPS set uses the 2018 expectation (for the founder).** `envelope.SPS` uses 3 m horizontal and 5 m vertical 95 % ("well-designed receivers", SPS PS 2020 introduction), not the standard's 8 m and 13 m. `SPS_WORST` (15 m and 33 m, the worst-site standard) is a beyond-limit case.
- **Harness speed cap.** `sim.recoverable` calls `research/consistent_backup/harness.kinematic`, whose speed cap can land a rounding error above 15 m/s and fail `DroneState` validation; both matrix shards stopped on it. `recoverable` now lowers the harness's cap to 15 (1 − 10⁻⁹) m/s, as `sim._state` does, instead of editing the parked CBK code. Rows written before the stop are kept (the shards resume).
- **Results reported as run, nothing tuned.** In-limit, in-model: 0 losses of separation in 282 adaptive runs, of which 160 stayed monitor-silent throughout (the strict evidence); baseline (main as configured, `lag_s` = 0, no delay compensation) 81 of 141 in calm air. Beyond-limit: the monitor fired its own alarm in B1–B5 and B7, not in B6 (doubled actuator lag; the known-lag assumption has no monitor). No beyond-limit case lost separation, so the matrix shows the alarms fire, not that they precede a loss. The baseline's zero losses in wind are a plant artefact (no airspeed drag term; the uncancelled wind carries all drones downwind together), so baseline-versus-adaptive is compared in calm air only. Details in P3-SA-03 §6.
